# Backend Engineering Standards & Architecture

**Project:** Voyager API (Agentic Orchestrator)
**Role:** Senior Backend Engineer
**Stack:** Node.js, Express, BullMQ, Mongoose, LangChain
**Version:** 2026.1.1 (Refined)

## 1. Core Philosophy: "Layered Architecture"

We strictly separate **Transport** (HTTP), **Business Logic** (Service), and **Data Access** (Repository). This prevents "Controller Bloat" where a single file handles validation, database queries, and AI calls.

- **Controller:** Dumb. Validates Input -> Calls Service Fdna-> Returns JSON.
- **Service:** Smart. Orchestrates the AI, Queue, and Logic.
- **Repository:** Database Only. Handles Mongoose queries. No logic allowed.

## 2. Directory Structure & File Limits

We strictly follow the Domain Grouping defined by the Architect.

### 2.1 The "Rule of 200" (Maintainability)

**Hard Rule:** If a file exceeds **200 lines**, it must be refactored immediately.

- **Controller too big?** Move logic to `services/`.
- **Service too big?** Split into sub-services (e.g., `TripGeneratorService.ts`, `TripPricingService.ts`).
- **Repository too big?** Split queries into specific scopes.

```text
api/src/
├── config/              # Env vars (validated via envalid) & DB connection.
├── features/            # BUSINESS DOMAINS
│   ├── planner/         # Corresponds to Frontend 'features/planner'
│   │   ├── controllers/ # HTTP Handlers (req, res).
│   │   ├── services/    # Business Logic (Talks to AI, Queue).
│   │   ├── repositories/# Database Access (Talks to Mongoose).
│   │   ├── jobs/        # BullMQ Worker Processors.
│   │   └── schemas/     # Zod Validation for Requests.
│   └── auth/            # Auth logic
├── middleware/          # Global Error Handling, Auth guards.
├── lib/                 # Shared utilities (Logger, Queue Factory).
└── main.ts              # Entry point.

```

## 3. The "Fire & Listen" Contract (Async Architecture)

The Frontend expects immediate feedback. We never block the HTTP request for long-running AI tasks.

### 3.1 Producer (The API)

- **Endpoint:** `POST /api/trips`
- **Action:** Validate Zod -> `tripQueue.add()` -> Return `{ jobId }` immediately.
- **Constraint:** The Controller **NEVER** `await`s the AI generation. It only `await`s the Queue addition.

### 3.2 Consumer (The Worker)

- **Concurrency:** We process **5 jobs max** concurrently to respect OpenAI rate limits.
- **Progress:** You **MUST** call `job.progress(number)` at every step (25%, 50%, 75%) so the UI spinner updates.
- **Partial Results:** Save intermediate steps to Redis/Mongo so the user sees "Drafts" appearing in real-time.

## 4. Resilience, Logging & Self-Healing

Distributed systems fail. We design for failure.

### 4.1 Structured Logging (Observability)

We do not use `console.log`. We use a structured logger (e.g., `Pino` or `Winston`).

- **Rule:** Every log must include a `correlationId` (Request ID) or `jobId`.
- **Why:** This allows us to trace a single request from the API -> Queue -> Worker -> Database.

```typescript
// ✅ GOOD
logger.info(
  { jobId: job.id, event: "AI_GENERATION_START" },
  "Starting trip generation",
);
```

### 4.2 Circuit Breakers

Wrap all external calls (Google Places, OpenAI) in `opossum` or similar.

- **Strategy:** If the Weather API fails 5 times in 10 seconds, **Open the Circuit** (stop calling it) and return `weather: null` immediately to save resources.

### 4.3 AI Retry Loop (Self-Correction)

AI output is unpredictable. We wrap LangChain calls in a "Reflection Loop."

1. **Attempt 1:** Ask AI for JSON.
2. **Validate:** `JSON.parse(output)`.
3. **Failure:** If it fails, catch the error, feed it back to the AI ("You returned invalid JSON. Fix it."), and retry.
4. **Give Up:** After 3 attempts, fail the job gracefully and alert the user.

## 5. Security & Validation (Zero Trust)

### 5.1 Config Validation

The app must **crash on startup** if environment variables are missing.

- **Tool:** Use `envalid` or `Zod` in `src/config/env.ts`.
- **Rule:** `OPENAI_API_KEY` must be checked before the server starts listening.

### 5.2 Input/Output Sanitization

- **Input:** Middleware validates `req.body` against a Zod schema. Extra fields are stripped.
- **Output:** Run `sanitize-html` on **any** string generated by AI before saving to MongoDB. We assume the AI is trying to XSS us.

### 5.3 CORS Configuration

- **Headers:** Whenever adding a new custom header to API requests (e.g., `x-idempotency-key`), you **MUST** remember to add it to the `allowedHeaders` array in `index.ts` CORS configuration to prevent preflight errors from the frontend.

### 5.4 Mongoose Schema Defaults (Anti-Pattern Warning)

- **Issue:** When creating documents with nested fields that have schema defaults (e.g., `notificationPreferences: { tripReminders: { type: Boolean, default: true } }`), never pass the raw schema object `{ type: true, default: true }` during creation.
- **Why:** Mongoose parses this as trying to cast the entire object `{ type: true, default: true }` to a single Boolean, causing a `Cast to Boolean failed` exception and returning a `500` or `404` error if it happens during a fallback sync.
- **Rule:** Always assign plain values (`true` or `false`) to Boolean fields when calling `.create()` or `.update()`.

### 5.5 Pino Logger "Empty Error Object" Warning

- **Issue:** Using `logger.error({ error }, "message")` when `error` is a raw JavaScript `Error` object will result in Pino printing `{}` (an empty object), hiding the stack trace.
- **Why:** JavaScript native `Error` objects do not have enumerable properties (like `message` or `stack`), so `JSON.stringify` (which Pino uses under the hood) renders them as `{}`.
- **Rule:** Always deconstruct or use `err` property: `logger.error({ err: error, error: error.message, stack: error.stack }, "message")` or rely on the standard `err` key which Pino automatically formats: `logger.error({ err: error }, "message")`.

## 6. Itinerary Builder Protocol (Lessons Learned — Do Not Skip)

The itinerary pipeline has specific anti-patterns that have caused production bugs. Treat these rules as mandatory.

### 6.1 The Correct Pipeline Order (Non-Negotiable)

```
AI intents
  → flattenIntents()          # preserves day→slot order
  → validateBatch()           # resolves text queries → real coordinates
  → [deficit check + fill]    # guard: validated.length must equal intentList.length
  → buildTaggedPlaces()       # tag each ValidatedPlace with its slot intent
  → clusterByProximity()      # greedy geo-cluster, then sort within cluster by slotOrder
  → buildItinerary()          # assign day clusters to time slots
```

Never rearrange this order. Never skip a step.

### 6.2 Never Use a Global Round-Robin Index

**Forbidden pattern — causes place duplication:**

```typescript
// ❌ BAD: wraps around when validated.length < total slots → repeats places
const place = validated[globalIdx];
globalIdx = (globalIdx + 1) % validated.length;
```

**Required pattern — each day consumes its own slice:**

```typescript
// ✅ GOOD: per-day index, never wraps across days
const dayPlaces = clusters[dayNum] ?? [];
const place = dayPlaces[dayIdx++]; // undefined when cluster is exhausted → if(place) skips gracefully
```

### 6.3 Always Check Validation Yield (Deficit Guard)

AI generates N intents. Google Places validation may resolve fewer than N.
If `validated.length < intentList.length`, empty slots appear silently.

**Required:**

```typescript
const deficit = intentList.length - validated.length;
if (deficit > 0 && validated.length > 0) {
  const supplementary = await aiAgentService.generateSupplementaryQueries(
    deficit,
    preferences.destination,
    validated.map((p) => p.name),
  );
  const extra = await validationService.validateBatch(
    supplementary,
    preferences.destination,
  );
  validated = [...validated, ...extra];
}
```

### 6.4 Geo-Clustering Must Be Slot-Aware

AI prompt instructions alone ("group activities geographically") are **insufficient** — the AI does not know real coordinates at generation time.

**Required:** Implement algorithmic post-validation clustering (greedy nearest-neighbor).

**Critical constraint:** Cluster the `{place, slotType, slotOrder}` tuple — NOT raw `ValidatedPlace[]`.

```typescript
// ❌ BAD: pure coordinate clustering destroys slot intent
clusterByProximity(validated: ValidatedPlace[])
// → "evening restaurant" may end up in the morning slot

// ✅ GOOD: tag first, cluster second, sort by slotOrder within each cluster
const tagged = buildTaggedPlaces(intents, validated); // preserves morning/afternoon/evening metadata
const clusters = clusterByProximity(tagged);          // sort(a,b => a.slotOrder - b.slotOrder) within each cluster
// → morning-type places always lead the day, evening-type always close it
```

### 6.5 Geo-Validator is Diagnostic Only

`geoValidatorService.validateDistance()` sets `requiresTransport` and `distanceFromPrevious` flags.
These are **display metadata for the frontend** — they never trigger re-grouping or re-ordering.
Clustering must happen before `buildItinerary`, not inside it.

## 7. Production Build Verification (Non-Negotiable)

**Every agent MUST ensure the project builds successfully for production before considering any task complete.**

```bash
# Run from the repo root — must exit with 0 errors
npm run build
```

- **Zero Errors:** The build **MUST** produce zero TypeScript errors, zero ESLint errors, and zero bundler errors.
- **No Warnings Allowed:** Treat every compiler/bundler warning as an error. Fix it, do not suppress it.
- **When to Run:** After every meaningful code change — not just at the end of a task.
- **Failure = Blocked:** If `npm run build` fails, stop all other work and fix the build first.

## 8. Development Checklist (PR Review)

Before merging backend code, verify:

- [ ] **Production Build:** Does `npm run build` pass with **zero errors**? (Mandatory gate)
- [ ] **File Size:** Is any file >200 lines?
- [ ] **Layer Violation:** Does a Controller talk to Mongoose directly? (Reject PR).
- [ ] **Async Safety:** Is `await` used inside a `forEach` loop? (Use `Promise.all` instead).
- [ ] **Observability:** Are logs structured with `jobId`?
- [ ] **Config:** Are new env vars added to `env.ts` validation?
- [ ] **Sanitization:** Is AI output scrubbed before DB save?
- [ ] **Itinerary Pipeline:** Is the 5-step order respected? (intents → validate → deficit fill → tag+cluster → build)
- [ ] **No Global Index:** Is any itinerary slot assigned via a global modulo counter? (Reject PR).
- [ ] **Slot-Aware Clustering:** Does clustering preserve `slotType` metadata and sort within clusters?
- [ ] **Deficit Guard:** Is `validated.length` compared against `intentList.length` before building?
